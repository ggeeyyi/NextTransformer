截至 2026-11-05。本页记录 Arena v1 及其相关工作为 Arena v2 打下了哪些基础。还没做的工作见 [路线图](arena-v2-roadmap.zh-CN.md)；详细的工作流设计见 [arena-v2-agent-workflow.zh-CN.md](arena-v2-agent-workflow.zh-CN.md)；证据在 [`evidence/checks/arena-v1/`](../../evidence/checks/arena-v1/README.md) 及其旁边的各阶段目录里。英文版：[arena-v2-explored.md](arena-v2-explored.md)。

## Arena v1：一次有人监督的研究过程（2026-10-30 至 2026-11-05）

1. **研究 gym 在真实数据上的验收（Stage 0）。**
   - gym 的训练和正式训练器一致：第 1 步 loss 相等，第 300–510 步平均 \|Δloss\| 不超过 0.0039。
   - 计划内分段和突然中断后都能续训；FLOPs 精确结算；最终 dev BPB 为 0.887221，不中断的运行为 0.887830。
   - 账本和审计成本一致；验证集和 CORE 的数值从不到达 agent；新起的服务能从存储中恢复状态。
   - 花费：41.6 平台 GPU 时。
2. **代理规模的可信度（Stage 1）。**
   - 512 步的压缩调度只能用来筛选：Spearman 0.40、配对准确率 0.674，要求是 0.85 / 0.9。
   - 2,000 步的恒定学习率前缀能排名：在已发布曲线上回测达到 0.918 / 0.935。
   - 同一初始化的重复运行在第 512 步只差 0.00009。
   - 花费：110.4 GPU 时。
3. **候选搜索（Stage 2）。**
   - Claude 通过 gym 的工具提出、编写并挑选候选，规则在第一个作业之前预登记：
     - 第 512 步筛选：比 `dense_full` 高 0.030 以上就取消；
     - 第 2,000 步排名；
     - 胜出：比最好的锚点低 max(2δ, 0.001) 以上，δ = 0.00041。
   - 共 17 次运行、三轮。第 1 轮没有单项改动胜出，第 2、3 轮靠组合接近胜出的改动取胜。
   - 最好的是 `attnres_full_canon_abcd`，比 `attnres` 低 0.0038。门控、更深的层数、每层都加 value embedding 以及 MoE FFN 都没有带来提升。
   - 花费：549.7 GPU 时，墙钟时间 24.1 小时。
4. **移植与核对（Stage 3）。**
   - 两个最好的候选手工移植成方法插件并完成校准（相对锚点 +0.337% 和 +0.486%），附成本证明和测试。
   - gym 和正式训练器的前几步逐位相等，第 300–510 步平均 \|Δloss\| 为 0.0033–0.0041。
   - 花费：42.1 GPU 时。
5. **胜出者的正式训练（进行中）。**
   - 先通过了 32 卡有界检查：第 1 步 loss 与 8 卡运行相同，每步 2.98 秒（扩展效率 95%）。
   - 第一段在第 39,500 步因作业时限结束，第二段从第 39,000 步的 checkpoint 续训。
   - 第 39,500 步时验证集 BPB 为 0.6819，在 34 个运行中排第一：
     - 比 `mhc` 低 0.0014，自第 10k 步起一直稳定；
     - 比 `attnres` 低 0.0032，在衰减阶段收窄；`mhc` 对 `attnres` 的领先也同样在收窄。
   - CORE：第 8k–32k 步依次为 0.232 / 0.240 / 0.279 / 0.292。第 32k 步与 `mhc` 持平，比 `attnres` 高 0.016。
   - 预计最终验证集 BPB 为 0.660–0.661；最好的已发布运行 `mhc` 最终为 0.6617。

## 这些证据对 v2 意味着什么

1. **早筛选，晚排名。** 512 步能淘汰明显差的候选，但排不了名。衰减会让接近的方案换位：我们对 `attnres` 的领先从 −0.0057（第 10k–22k 步平均）收窄到 −0.0032。
2. **seed 噪声未知。** δ 只测到了 GPU 非确定性，因为 seed 偏移没有改变初始化。
3. **BPB 和 CORE 的分歧与机制有关。** 在 23 个完整的已发布运行上，二者有 83% 的配对排序一致（Spearman 0.85）。固定大小状态的 mixer 在需要从上下文读答案的任务上吃亏。v1 胜出者在 BPB 上领先 `mhc`，CORE 却持平。
4. **选型没有考虑效率。**
   - 训练：在 gym 里（未开 `torch.compile`），胜出者每步耗时是 `attnres` 的 1.66 倍，审计 FLOPs 只多 0.48%。
   - 正式训练在 32 卡上每步 3.01 秒，MFU 约 35%，峰值显存 97.9 GiB。
   - 推理成本从未测量。
5. **以下步骤由人完成：** 批准计划、审阅预登记规则、设定算力上限、决定何时停止、移植，以及操作正式训练。
6. **记录有缺口。** 运行、账本和归档都保存了，但 LLM token 用量、费用和网络访问没有计量。
7. **运维经验。**
   - 多节点时，训练器按各 rank 自己时钟计算的时限会让不同 rank 停在不同步数，所以每段改为在作业时限处结束。
   - 收尾过程不能续训，所以作业时限不能落在最终评测期间。
   - 排队占了大部分墙钟时间：Stage 2 每次运行排队 3.4–5.4 小时。

## 已经建成的工具

| 方面 | 状态 |
|---|---|
| 研究 gym（`nextt_gym/`） | 22 个操作，支持 MCP、HTTP 和 Python；四种规模（正式前缀和压缩调度下各 512 步、2,000 步、完整长度）；带平台 GPU 时的 FLOPs 账本；归档、谱系和排行榜；封存；给进化搜索框架用的 `evaluate()` 适配器 |
| 集群后端 | 分段作业、失败后从 checkpoint 重启、GPU 时计量；用于 37 次运行，约 700 GPU 时 |
| 正式训练工具 | 带 rendezvous 的多节点启动；带收尾保护的分段提交；监控脚本 |
| 披露 | 从归档生成披露卡草稿 |
| 进度页面 | 各阶段图表、谱系树、正式训练跟踪；可作为演化看板的原型 |
