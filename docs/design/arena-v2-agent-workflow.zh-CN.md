# Arena v2 agent 研究工作流：路线图草案

**状态：** 讨论稿 v0.1，2026-11-05。英文版：[arena-v2-agent-workflow.md](arena-v2-agent-workflow.md)。

摘要：[已经探索的内容](arena-v2-explored.zh-CN.md)和[路线图](arena-v2-roadmap.zh-CN.md)。

**范围。** 本文讲 agent 在一次 Arena v2 会话里运行的研究循环：怎样读历史、提出、测试和挑选一个架构，怎样提交，
以及过程中记录什么。这个循环运行的环境在别处规定：
- Harbor 任务和 Gym API 见 [roadmap](../src/content/docs/roadmap.md)（#24）；
- Gym 的草稿实现见 [#25](https://github.com/Interactive-Active-AI/NextTransformer/pull/25)。

本文只列出工作流对环境的需求（§9）。

## 1. 需求

| # | 需求 | 本稿对应部分 |
|---|---|---|
| R1 | 以 Arena v1 的研究工作流为基础 | §2 概括 v1。§5 沿用它的阶段、预登记规则和证据，并把人工操作员做的步骤换成 Gym 操作和冻结的自我预登记 |
| R2 | agent 可以读所有历史结果和历史运行，可以联网；优化目标是 BPB；研究过程中看不到自己方案的 CORE-22 分数 | §3 |
| R3 | 设计新架构时考虑训练效率和推理效率（[issue #19](https://github.com/Interactive-Active-AI/NextTransformer/issues/19)） | §6 |
| R4 | 记录每次会话的完整轨迹 | §7 |

**优化目标。** 在不变的协议下，正式训练第 46,875 步的验证集 BPB 最低。协议包括：
- 相同的数据、数据顺序和 tokenizer；
- 2,048 上下文、49.152B 输入 token、seed 42；
- 固定的优化器和学习率调度；
- 每输入 token 的训练 FLOPs 与锚点相差不超过 ±1%。

CORE-22 作为留出的测试集，在会话结束后报告。这一点与已合并的 roadmap 不同：roadmap 里最终评分只看 CORE-22（决策 D2）。

## 2. 起点：Arena v1 的工作流

Arena v1（2026-10-30 至 2026-11-05）是一次有人监督的研究过程：Claude 通过研究 gym 的工具担任研究者，由一位人员批准每个阶段的计划、规则和算力。证据见 [`evidence/checks/arena-v1/`](../../evidence/checks/arena-v1/README.md)。

| 阶段 | 问题 | 规则与结果 | 平台 GPU 时 |
|---|---|---|---:|
| 0. 工具验收 | gym 在真实数据上的训练和正式训练器一致吗？续训、计量和封存是否正确？ | 四项预登记检查（A1–A4）全部通过 | 41.6 |
| 1. 代理验证 | 便宜的短跑能按最终 BPB 给方法排名吗？ | **512 步压缩调度：** Spearman 0.40、配对准确率 0.674，要求是 0.85 / 0.9，所以只能用来筛选。<br>**2,000 步恒定学习率前缀：** 在已发布曲线上回测达到 0.918 / 0.935 | 110.4 |
| 2. 搜索 | 哪个改动能胜过两个锚点？ | **运行：** 2,000 步规模 17 次，分三轮，每个候选只做一项主要改动。<br>**512 步筛选：** 比 `dense_full` 高 0.030 以上就取消。<br>**胜出：** 比最好的锚点低 max(2δ, 0.001) 以上，δ = 0.00041。<br>**停止：** 三轮后、用满 600 GPU 时，或连续两轮没有胜出者。<br>**结果：** 4 个胜出，最好的 `attnres_full_canon_abcd` 比 `attnres` 低 0.0038 | 549.7 |
| 3. 移植与核对 | 胜出者作为方法插件训练时还一致吗？ | 手工移植成插件；前几步逐位相等，第 300–510 步平均 \|Δloss\| 为 0.0033–0.0041 | 42.1 |
| 正式训练 | 完整 46,875 步后领先还在吗？ | 32 卡，分两段，进行中。<br>**第 39,500 步：** 验证集 BPB 0.6819，34 个运行中第一。<br>**比 `mhc`：** −0.0014，从第 10k 步起一直稳定。<br>**比 `attnres`：** −0.0032，在衰减阶段收窄；`mhc` 对 `attnres` 的领先同样在收窄。<br>**第 32k 步 CORE：** 0.292，`mhc` 为 0.293 | 约 1,400（预计） |

影响 v2 设计的经验：
1. **早筛选，晚排名。** 512 步能淘汰明显差的候选，但排不了名。2,000 步前缀在已发布曲线上排名效果好，但学习率衰减会让接近的方案换位：我们对 `attnres` 的领先从 −0.0057（第 10k–22k 步平均）收窄到衰减期的 −0.0032。
2. **噪声估计测错了对象。** δ 测到的是 GPU 非确定性，因为 seed 偏移没有改变初始化。不同 seed 之间的方差仍然未知。
3. **选型没有考虑效率。** 在 gym 里，胜出者每步耗时是 `attnres` 的 1.66 倍（11.33 秒对 6.82 秒，未开 `torch.compile`），审计 FLOPs 只多 0.48%。协议不给速度打分，但速度决定了正式训练的 GPU 时；推理成本则完全没有测量。
4. **BPB 和 CORE 的分歧与机制有关。** 在 23 个完整的已发布运行上，最终验证集 BPB 和 CORE 有 83% 的配对排序一致（Spearman 0.85）。固定大小状态的 mixer 在需要从上下文读答案的任务上吃亏。v1 胜出者在 BPB 上领先 `mhc`，CORE 却持平。
5. **有人做了 v2 必须自动化或记录的步骤：** 批准计划、预登记规则、算力上限、决定何时停止、移植，以及操作正式训练。
6. **移植花掉了整整一个阶段。** v2 的候选就是原生插件（#25），研究用的代码就是提交的代码。
7. **记录不完整。** 运行、FLOPs 账本和归档都保存了，但 LLM 轮次、token 用量、费用和网络访问没有计量，披露卡里也写明了这一点。

|---|---|---|---|
| 已发布结果 | `results/runs/` 中每个运行的 189 个验证点、6 个 CORE 点、最终 BPB 和训练算力 | 可读 | 历史背景，包括历史 CORE |
| 证据 | 审计、成本证明、模型卡、方法源码和准入配置 | 可读 | 通过 Gym 的历史和参考操作读取（#25 的 `list_experiments`、`read_experiment`、`read_reference`） |
| 研究历史 | Arena v1 的研究运行（512 步和 2,000 步的曲线）、各阶段报告、失败记录，以及以往已公开会话的轨迹 | 可读 | 让 agent 不必重做 Stage 1 就有代理规模可信度的证据 |
| 互联网 | 论文、代码、讨论 | 允许，并记录（§7） | 公开的 CORE 数据和排行榜页面都能访问到，所以靠记录而不是拦截 |
| 本会话的运行 | 训练 loss、研究用 BPB、效率指标、checkpoint | 可读 | 只有所属会话能看 |
| 本会话候选的 CORE-22 | — | 会话期间**一律看不到** | 研究 profile 从不评测 CORE。提交方案的正式训练会在 6 个点评测 CORE，这些值在会话关闭前不进入 agent 的工具、日志，也不在它能触及的地方 |

**需要堵住的 CORE 泄露途径**（agent 能上网）：
- 正式训练的实验跟踪（例如 W&B）设为私有，凭证不放进 agent 容器；
- 会话关闭前，不发结果 PR、不更新排行榜、不公开正式训练的日志；
- 研究作业的日志只保留 profile 允许公开的指标；
- 历史在会话开始时冻结（cohort 快照），会话期间新发布的结果不算新反馈。

**研究阶段 agent 看哪个 BPB（决策 D1）：**
- **(a) 推荐。** 像 v1 一样用 dev 集 `shard_06541`，验证集 `shard_06542` 一直不碰，直到最终训练，这样最终 BPB 也是留出的数字。既然目标就是 BPB，我们推荐这一项。
- **(b)** 像 #24、#25 一样直接用验证集。这样最终 BPB 不再是留出的，CORE 是唯一的留出信号。

## 5. 工作流

一次会话就是一次 Harbor trial。各阶段沿用 v1 的阶段划分，每个阶段结束时产出一份记入轨迹（§7）的产物。

**P0. 熟悉情况**（只用 CPU，不消耗研究 FLOPs）
- 读 `describe_space`、`get_resources`、`get_budget`。
- 建立一个**库（bank）**：所有历史运行整理成一张表，包括机制标签、最终 BPB、曲线形状、衰减期增益、FLOPs 构成和效率指标。
- 诊断当前前沿：哪些机制领先、曲线在哪里交叉、各运行的效率位置。
- 产物：研究计划。

**P1. 预登记**（只用 CPU）
- 开始训练前写定并冻结：
  - 代理规模的档位，以及筛选和排名规则；
  - 噪声估计方案；
  - 效率门槛（cohort 规定的，加上自己定的）；
  - 预算分配、停止规则和最终选择规则。
- 每条代理规则先在已发布曲线上回测。默认采用 v1 的证据：在 512 步筛选，在正式前缀的 2,000 步或更长处排名。
- 规则通过 Gym 保存，由服务端打时间戳并计算哈希。只允许在受影响的运行开始之前修改，并且必须写明原因（沿用 v1 的做法）。
- 这一步用可审计的承诺取代 v1 里的人工批准。

**P2. 锚点和噪声**（约占预算 15%）
- 在排名档位上跑锚点：BPB 最好的已发布运行（目前是 `mhc`），以及 agent 要在其上改进的方法（如果不是同一个）。
- 再跑一次换初始化 seed 的重复运行（v1 没有做到），估计 seed 噪声 δ_seed。v1 测得的 GPU 非确定性 0.00041 作为下限保留。

**P3. 生成候选**（只用 CPU）
- 使用早期研究循环设计里的几种操作：互补、移植、修补、重新分配、消融，以及从文献或网上引入（注明来源和版本）。
- 每个候选相对一个指定的父方案只做一项主要改动，并写下预测：在该档位上的差距，以及各项效率指标会变好还是变差。
- 花算力之前：
  - 用 `inspect_cost` 检查每 token FLOPs，用 `calibrate_candidate` 校准到 ±1% 以内；
  - 计算 §6 中的静态效率指标；
  - 和已注册的方法比对，确认是新方案；
  - 违反门槛的候选直接淘汰。

**P4. 逐轮淘汰式的筛选和排名**（约占预算 60%）
1. 每个候选训练到第 512 步，按规则筛选。
2. 通过筛选的候选从各自的 checkpoint 续训（#25 的续训功能）到第 2,000 步，然后排名。
3. 排名靠前的几个继续续训到更长的档位（例如 8,000 步），或者走一段短衰减分支（决策 D5），检查衰减期排名会不会变。
4. 每次运行都测量训练效率（§6）。

下一轮的候选池来自对本轮结果的诊断。v1 第 2、3 轮的胜出者正是把接近胜出的改动组合起来得到的。

**P5. 确认**（约占预算 20%）
- 最终候选在排名档位上换第二个 seed 重跑，或者继续续训到更长。
- **胜出规则：** 平均差距比最好的锚点低 max(2·δ_seed, 0.001) 以上，并且通过所有效率门槛。差距在噪声以内的候选，选效率更高的那个。
- 报告一共筛过多少个候选，用来衡量"赢家诅咒"。

**P6. 冻结提交**
- 在最终 profile 上运行 `validate_candidate`（准入要求 ±1% 以内），然后 `finalize` 生成收据，会话结束。
- Gym 从头训练这个候选。CORE 评测结果不对外，任何结果可见之前会话就已经关闭。

**P7. 揭晓与反思**（正式训练结束后）
- 平台公布最终 BPB、CORE、效率指标和轨迹。
- **跨会话的自我改进**（RSI 的部分）：研究层可以在会话之间改变，包括候选生成的启发式、代理档位和优先级规则。一项改动只有在相同预算下、在一个封存的 cohort 上比冻结的旧版本找到更好的架构，才会被采用；预测误差更低本身不算数。评测层永远不变。

**预算。** 单位是正式训练当量（FRE）：1 FRE = 46,875 步 ≈ 2.3×10²⁰ 训练 FLOPs。v1 的 Stage 0–2 用了约 0.9 FRE 的训练步数。建议每次会话默认 **1 FRE**（决策 D4），分配如下：

| 占比 | 阶段 |
|---:|---|
| 15% | P2 锚点和噪声 |
| 60% | P4 搜索（含要扣算力的检查） |
| 20% | P5 确认 |
| 5% | 预留 |

## 6. 训练效率和推理效率

每项指标都标明是实测、估计还是未知。实测值要写明硬件、卡数、micro batch、编译设置和软件版本，这也是 issue #19 中维护者提出的做法。

| 类别 | 指标 | 来源 |
|---|---|---|
| 训练 | 每 token 训练 FLOPs（固定在 ±1% 以内） | 账本、`inspect_cost` |
| 训练 | 每步耗时、正式 batch 下每卡 tokens/s、MFU | 在研究运行中实测；`nexttransformer.native.benchmark` |
| 训练 | 峰值显存；放得下的最大 micro batch | 实测 |
| 推理 | 参数量（总量，以及 MoE 每 token 激活的参数量）；权重字节数 | 静态 |
| 推理 | 2k 上下文的 prefill FLOPs；2k、8k、32k 上下文下每个解码 token 的 FLOPs | 静态：backbone 自带的估算函数，有 spec 时用 HuggingArch（[#21](https://github.com/Interactive-Active-AI/NextTransformer/pull/21)） |
| 推理 | 2k 和 32k 下每 token 及每条序列的 KV cache 或状态字节数；每解码一个 token 要读的字节数（权重加缓存），作为显存带宽的代理指标 | 静态 |
| 推理（可选） | batch 1 和 batch 64 下的解码 tokens/s；2k 的 prefill 延迟 | 在参考硬件上实测 |

**效率怎样进入决策：**
- **硬门槛**，按 cohort 设定（决策 D3），在训练前检查。以下数值仅作示意：
  - 相同设置下每步耗时 ≤ `dense_full` 的 1.5 倍；
  - 正式 micro batch 下峰值显存不超过单卡容量；
  - 32k 下每 token 的 KV 或状态字节数 ≤ `dense_full`；
  - 8k 下解码 FLOPs ≤ `dense_full` 的 1.2 倍。
- **平局判定：** 差距在噪声以内的候选，选效率更高的。
- **报告：** 画出 BPB 对训练 tokens/s、BPB 对每解码 token 字节数的 Pareto 图，包含所有候选和所有已发布运行。最终报告把胜出者的效率和 `dense_full`、以及最好的已发布运行对比。
- **候选组合：** 在几类推理成本不同的机制里都保留候选，避免搜索全部收敛到最贵的一类。这几类是全注意力、稀疏或局部注意力、线性状态、混合结构，以及跨层共享 KV（例如 issue #19 提到的 YOCO）。
- **对照 v1：** `attnres_full_canon_abcd` 在 gym 里每步耗时是 `attnres` 的 1.66 倍，需要过每步耗时这道门槛。

## 7. 轨迹记录

每次会话产出一份**轨迹包**。轨迹包只能追加、带哈希链，由平台保存，脱敏后和结果一起公开。

| 层面 | 记录内容 | 由谁收集 |
|---|---|---|
| Agent | 每次模型调用：输入、输出、工具调用和返回、模型 ID、token 用量、费用、时间戳 | Harbor 原生的轨迹记录（#25） |
| 工作区 | shell 命令、写过的文件、候选草稿；容器运行时快照 | Harbor 运行时快照，以及最终工作区的归档 |
| 网络 | 每次搜索的查询词和打开的 URL，附时间和内容哈希 | agent 容器出网流量上的记录代理 |
| Gym | 每次 API 调用和返回、候选包、报价、作业、结果、账本、效率测量 | Gym 存储和签名证据（#25） |
| 决策 | 研究计划、预登记规则和修订；假设及其预测；每次选择时用的规则和证据 ID | 新增的 Gym 操作 `record_decision`，由服务端打时间戳，不可修改 |
| 人 | 操作员的每次操作及原因 | 操作员日志 |

**用途：**
- **披露卡：** 从轨迹包自动生成，包括 LLM token 用量和费用，补上 v1 的缺口。
- **Anti-hack 审查**（roadmap 中的"之后"）：查有没有试图获取 CORE、访问封存页面或本会话的结果页面、试图改动评测、挑 seed，或者没有证据支撑的结论。
- **演化看板**（roadmap 中的"之后"）：Arena v1 的进度页面（谱系树、曲线、各阶段算力）可以作为原型。
- **自我改进：** 轨迹包是跨会话自我改进（P7）的输入。

## 8. 防护措施

| 风险 | 防护 |
|---|---|
| agent 改动测量方式 | 协议和评测层不在它的写权限内；候选是插件，准入会检查成本和指纹 |
| CORE 变成开发信号 | 研究阶段从不计算 CORE；正式训练的 CORE 在会话关闭前不对外；实验跟踪设为私有、日志过滤；网络访问记录在案并事后审查 |
| 看了结果再调规则 | P1 预登记；修订必须在受影响的运行开始之前记录 |
| 不计费的算力 | Gym 的预算覆盖检查、失败和取消（#25） |
| 赢家诅咒和 seed 运气 | 最终候选跑第二个 seed；报告筛过多少候选；最终训练固定 seed 42，不载入研究阶段的权重 |
| 效率被 BPB 掩盖 | 训练前检查门槛、报告 Pareto 图、在不同推理成本类别里都保留候选 |

## 9. 工作流对 Gym 的需求

| 需求 | #25 现状 | 缺口 |
|---|---|---|
| 在 GPU 上以正式尺寸跑研究，并能同时跑多个 | 本地 CPU worker，一个槽位 | 需要 GPU 集群适配器。Arena v1 的集群后端（分段运行、从 checkpoint 重启、GPU 时计量）可以提供 |
| agent 自选训练长度并续训 | 已有（`target_update`、`checkpoint_id`） | — |
| 从 checkpoint 分出一段短衰减 | 没有 | 增加对应的研究 profile（D5） |
| `inspect_cost` 和 `get_result` 返回效率指标 | 只有成本报告 | 加上 §6 的指标及其标注 |
| 研究历史 | 只有已发布运行 | 加入 Arena v1 的研究运行和以往已公开的轨迹 |
| 决策日志 | 没有 | `record_decision` |
| 正式训练的 CORE 不让会话看到 | 最终训练适配器会运行正式训练 | 把它的 CORE 评测、日志和实验跟踪都与会话隔开 |
| 网络访问日志 | 没有 | agent 容器出网的记录代理 |
