# Arena v2 agent 工作流：路线图

本路线图列出 Arena v2 agent 研究工作流还需要探索和建设的内容。已经知道的内容见 [arena-v2-explored.zh-CN.md](arena-v2-explored.zh-CN.md)；详细设计见 [arena-v2-agent-workflow.zh-CN.md](arena-v2-agent-workflow.zh-CN.md)。运行环境（Harbor 任务和 Gym API）以项目 [roadmap](../src/content/docs/roadmap.md) 和草稿 Gym [#25](https://github.com/Interactive-Active-AI/NextTransformer/pull/25) 为准。英文版：[arena-v2-roadmap.md](arena-v2-roadmap.md)。

## 2026 年 11 月 14 日前：Arena v2 的 agent 工作流

1. **定下优化目标和访问规则。**
   - agent 在不变的协议下优化验证集 BPB。CORE-22 作为留出的测试集，会话结束后报告。
   - agent 可以读所有已发布结果和运行、Arena v1 的研究运行和各阶段报告，也可以上网；网络访问会被记录。
   - 研究期间看不到自己候选的 CORE-22 分数：研究 profile 不评测 CORE，正式训练的 CORE 评测、实验跟踪和日志在会话关闭前一律封存。
   - 历史在会话开始时冻结，会话期间新发布的结果不算新反馈。
2. **按预登记的阶段组织工作流。**
   - 熟悉情况、预登记、锚点和噪声、生成候选、逐轮淘汰（512 → 2,000 → 更长）、确认、冻结提交、揭晓。
   - 开始训练前，agent 通过 Gym 冻结自己的规则：代理档位、筛选和排名阈值、噪声估计方案、效率门槛、预算分配和停止规则。修订必须在受影响的运行开始之前记录。
   - 每个候选相对一个指定的父方案只做一项主要改动，并写下预测。
   - 默认预算为 1 个正式训练当量（46,875 步，约 2.3×10²⁰ 训练 FLOPs）：锚点和噪声 15%，搜索 60%，确认 20%，预留 5%。
3. **训练效率和推理效率。**
   - **训练：** 每次研究运行都实测每步耗时、每卡 tokens/s、MFU 和峰值显存，并记下硬件和设置。
   - **推理：** 参数量、prefill 和 decode FLOPs、每 token 的 KV 或状态字节数，以及每解码一个 token 要读的字节数（作为显存带宽的代理指标）。数据来自 backbone 自带的估算函数或 HuggingArch（[#21](https://github.com/Interactive-Active-AI/NextTransformer/pull/21)）。
   - **用法：** 按 cohort 设定硬门槛，训练前检查；差距在噪声以内时选效率更高的；与已发布运行一起画 Pareto 图；在几类推理成本不同的机制里都保留候选。
4. **完整的轨迹记录。**
   - 记录模型调用（Harbor 的轨迹）、工作区快照、经出网代理记下的网络访问、每次 Gym API 调用、通过新增的 `record_decision` 操作记下的决策，以及操作员的操作。
   - 每次会话的所有记录放进一个只能追加、带哈希链的轨迹包，并从中生成披露卡（包括 LLM token 用量和费用）。
5. **跑起来。**
   - 在 CPU fixture 上用 Harbor 和 Claude Code 把整个工作流演练一遍。
   - 通过 GPU 集群适配器在真实数据上跑一次有预算上限的 GPU 会话（约 0.1 个正式训练当量）。

之后：

- **第一次完整会话：** 1 个正式训练当量的研究，然后是最终训练；揭晓 BPB、CORE 和效率。
- **跨会话的自我改进：** 只有新版本在相同预算下、在封存的 cohort 上胜过冻结的旧版本时，才改动研究层（候选生成、代理档位、优先级）。
- 从轨迹包做 **anti-hack 审查** 和 **演化看板**。

## 待研究的问题

| 问题 | 已知情况 | 探索方法 | 成本 |
|---|---|---|---|
| 在 2,000 步前缀之后接一小段衰减，能否更好地给接近的候选排名？ | 衰减会让接近的方案换位：我们对 `attnres` 的领先从 −0.0057 收窄到 −0.0032 | 从锚点和 Stage 2 胜出者的 2,000 步 checkpoint 分出短衰减，与它们的最终结果对比 | 几次短跑 |
| 排名档位上的 seed 噪声有多大？ | 只测到了 GPU 非确定性（δ = 0.00041） | `dense_full` 和 `attnres` 在 2,000 步各再跑两个初始化 seed（第一个已由 Stage 2 提供） | 约 0.17 个正式训练当量 |
| 按 BPB 选型会不会损失 CORE？ | Spearman 0.85；固定状态的 mixer 在上下文任务上吃亏；v1 胜出者 CORE 与 `mhc` 持平 | 对比 v1 正式训练的最终结果；如果分歧持续，用非测试集的数据另建一个开发用能力评测集 | 只需评测 |
| 效率门槛定多少？ | v1 胜出者每步耗时是 `attnres` 的 1.66 倍；还没有推理数据 | 测量所有已发布方法的每步耗时和推理指标，按这个分布定门槛 | 静态分析加短时基准测试 |
| 代理规则对每类方法都成立吗？ | 不同类别曲线形状不同：线性 mixer 起步慢，循环结构起步快 | 在已发布曲线上按类别回测 512 步和 2,000 步的规则 | 只用 CPU |

## 当前实现与待完成工作

| 方面 | 现状 | 需要的改动 |
|---|---|---|
| Agent 工作流 | Arena v1 的工作流，每个阶段由人批准；v2 设计草稿 | 定下 D1–D8；把工作流冻结为 v0 |
| 候选格式 | 本地 gym：自定义模型格式，要手工移植。#25：原生插件 | 改用原生插件，不再手工移植 |
| 执行 | 本地 gym：GPU 集群后端。#25：一个本地 CPU worker | 基于 v1 的后端，为 #25 的 Gym 做 GPU 集群适配器 |
| 训练长度和续训 | 本地 gym：固定规模。#25：agent 自选目标步数，可从 checkpoint 续训 | 采用 #25 的做法；增加短衰减的研究 profile |
| 预算 | 本地 gym：FLOPs 账本，检查不计费。#25：检查计费，整数账本 | 采用 #25 的账本 |
| CORE 封存 | 本地 gym：在 API 层封存。#25：研究阶段从不评测 CORE | 正式训练的 CORE 评测、实验跟踪和日志也要与会话隔开 |
| 研究历史 | 本地 gym：导入的方法和自己的归档。#25：已发布运行 | 加入 v1 研究运行和以往的轨迹；每次会话冻结一份 |
| 效率 | 运行日志里有每步耗时和显存；静态的训练 FLOPs | 推理指标、实测/估计标注、门槛和 Pareto 报告 |
| 轨迹 | 运行、账本和归档，没有 LLM 和网络计量。#25：Harbor 轨迹和签名的 Gym 证据 | 出网代理、`record_decision`、带哈希链的轨迹包、自动生成披露卡 |
| 隔离 | 本地 gym：静态检查。#25：沙盒 worker | 沿用 #25；GPU 设备隔离按部署环境配置 |
| 最终训练 | 本地：人工准入加运维脚本。#25：`finalize` 加独立的单节点分派 | 基于 v1 的正式训练工具做多节点分派 |
